This repository owns the words and examples in this section. Edit `docs/` here, then open a pull request. The generated
`profile-recipes/` folder in `unset-sh/docs` is an output, not a second place to maintain the pages.

## The workflow

```text
source pull request -> validation and dry export -> merge to main
                                                       |
                                                       v
                                         docs-mirror environment
                                                       |
                                                       v
                                          replace profile-recipes/
                                                       |
                                                       v
                                    docs framework checks and deploys
```

1. **Validate.** The pull-request workflow typechecks the tools, runs tests, validates recipes, renders the catalogue
   and prepares an export in a temporary directory. It has no publishing key.
2. **Prepare.** On relevant `main` changes, or a manual run on `main`, `docs-mirror` repeats the checks. The exporter
   requires a clean committed checkout, rejects links and special files, and writes a new temporary folder.
3. **Publish the section.** The protected `docs-mirror` environment supplies `DOCS_DEPLOY_KEY`. The workflow checks out
   `unset-sh/docs`, replaces only `profile-recipes/` and verifies its staged paths. Before every normal Git push, it
   checks that all outgoing changes stay in that section and its files still match the generated export exactly.
4. **Build the site.** The docs repository owns Hugo, the shared theme and its deployment checks. A successful export
   is not by itself a successful site deployment; inspect that repository's build too.

The export contains Markdown, one existing developer preview, licence notices and `source.json`. Every Markdown page
links to its source commit. The manifest records original and exported file hashes so the generated bytes can be traced.
It carries no fonts, scripts or theme configuration.

## What changes automatically

Changes to these pages or their checked inputs trigger the mirror after merging to `main`. The workflow does not invent
new explanations when code changes. Changes to recipe behavior, schemas, limits or previews must include the relevant
documentation review in the source pull request. Keep the app-support revision explicit until that support is rechecked.

The mirror requires owner setup before its first successful run. Its existence alone does not mean the key is installed
or that this section is live. See the [publishing runbook](https://github.com/unset-sh/profile-recipes/blob/main/.github/DOCS-PUBLISHING.md)
for the setup and cutover checks.

## Failures and recovery

Validation or export failure stops before destination changes. A missing key stops before destination checkout. A
concurrent destination update gets up to three normal push attempts, with a rebase between attempts. Conflicts stop
the job for review. A clean rebase also stops if it moves an edit outside the section or changes the generated tree,
including a rename within the section. The workflow never force-pushes.

Fix the source through a pull request and rerun from current `main`. To undo bad content, revert its source change
through a pull request and export the corrected state. If the docs build fails, the previous successful site deployment
remains the reference while the failure is investigated. Do not fix a generated page by editing the mirror alone.
